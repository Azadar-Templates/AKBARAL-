## What is implemented now — not another connector

### 1. Actual deliverable-producing capabilities

- **Reusable JSON data-validation pack:** bounded client-authorized JSON export,
  required columns and a unique-key rule → standalone JavaScript validator,
  configuration, reproducible findings and usage instructions. Detects missing
  values, invalid/duplicate IDs, non-finite numbers and formula-risk warnings.
  Records are not changed or silently “cleaned.” No client values are embedded in
  the deliverable. Rules are client-agreed; findings need human business review.
- **Offline website release check:** supplied authorized HTML → exact input hash,
  source checks for title, language, viewport, heading count and missing image-alt
  attributes, plus explicit limitations. This is a heuristic source check, NOT
  browser rendering, WCAG certification, security testing or SEO ranking proof.

Limits: 128 KiB input, 5,000 JSON records, 20 required fields, 100 fields per record,
200 reported issues with honest total/truncation; one HTML document. No networking,
model API, shell, client-script execution, paid resource or deployment is invoked.
There is no claim that these limited services suit every client or guarantee sales.

The owner can **preview their own authorized non-sensitive sample** before any
customer exists. Such output is explicitly `owner_supplied_sample_not_customer_work`;
it creates no inquiry, paid job, customer count or cash. This can support truthful
capability demonstrations, not fabricated portfolio clients/testimonials.

### 2. Customer-acquisition preparation that humans can actually use

The private dashboard adds **Customers & work**. It presents the ten conditional
channels, two concrete service offers, owner-priced unpublished listing packs,
sample previews and an explicit-request intake form. Listing copy includes exact
scope, input requirements, exclusions, acceptance criteria and tool disclosure.
All prices are owner-set proposals, not forecasts or earnings.

Prepare the pack for an authentic eligible Fiverr/Upwork account, or respond to a
genuine inbound/consented-referral request. The owner reviews and publishes/replies
manually in the original permitted channel. No public page has been deployed and
no contact has been made. Absence of an approved property/account is not bypassed.
No lead-list purchase, scraping, bulk sender or recurring solicitation exists.

### 3. Demand → authenticated contract → useful work

`mission_customer_requests` records the actual incoming source reference, original
contact reference, observed date, owner review, time-bounded reply permission,
client brief, service configuration and exact proposed USD scope/hash. These are
explicitly **owner declarations**, not independently authenticated customer proof.
No source row is seeded. One prepared reply is persisted for recovery, never sent.
Opt-out/rejection suppresses that original channel/contact, stops all matching
requests and persists across restarts. No un-suppress endpoint exists.

An inquiry cannot execute paid work merely because the owner checks a box:

- Bind an already authenticated, authorized **existing** Fiverr order, Upwork
  fixed milestone or Contra direct escrow work item. Its owner/account, assigned
  agent, client, exact scope hash and gross contract amount must match.
- A marketplace-origin customer can only use its originating connector. An
  independently acquired direct client may use Contra; it cannot be silently
  moved into another channel. Upwork Project Catalog discovery does not magically
  turn a Catalog order into the narrower existing milestone lane: actual contract
  evidence must independently satisfy that connector or the binding is blocked.
- Direct inquiries can predate platform onboarding. When their original contact
  reference differs from the eventual authenticated Contra client ID, an explicit
  owner identity-mapping review is required and retained. This mapping is **still
  owner-reviewed acquisition attribution, not independent identity evidence**.
  Original contact/suppression identity remains unchanged; actual contract client
  identity comes from the existing connector, never request-body payment proof.
- Account and grant expiry, parent authority, agent status/freeze, software policy,
  kill switch and contact permission apply. Internal agent execution is limited to
  the exact assigned agent and requires enabled autonomy; the HTTP surface is
  owner-only. There is no new discovery/fulfillment daemon or unrestricted worker.
- Work is generated locally against authorized input. Only input hashes and the
  minimized output persist, not raw datasets/HTML. The brief/configuration and
  minimized findings require lawful retention permission. No automatic PII detector
  is claimed: owners must not submit sensitive data under this initial scope.
- Input corrections before quality approval create a new version/hash and preserve
  audit events. Owner approval binds exact output bytes; after approval it cannot
  be regenerated or silently replaced. Use those bytes through the existing
  connector's draft, approval, manual delivery and payment verification flow.

This initial bridge intentionally supports only the three fixed-work sources above.
Awin, Freelancer and Toptal retain all functionality and financial controls; they
are not relabeled as supported commercial-attribution bridges by this change.
Other categories are inventory/planning, not implemented fulfillment or payout.

### 4. Payment attribution without a new cash-admission route

`REAL CUSTOMER → REAL WORK → REAL PAYMENT → VERIFIED USD → MISSION WALLET`

The money side remains entirely in existing connectors. The customer workbench
never inserts money receipts, cash entries, earning jobs, invoices or payouts.
It reads exact existing work/delivery hashes, provider-confirmed state, payout,
canonical receiving receipt, completed money job and integrity-checked treasury
credit. Bank proof is independently verified by the original connector before
any of those records can represent genuine cash. One existing work item cannot be
bound to two inquiries. Reopening the workbench never creates another credit.

Quotes, inquiries, local artifacts, paid platform balances and pending bank
movements stay noncash. Under-review settlement is **zero currently verified** in
this workbench, with prior received net separately labelled historical. Verified
partial/full reversals reduce that history. Opt-out does not erase genuine past
receipts. Customer attribution is not current wallet balance or profit; allocations,
verified costs, liabilities, holds and owner-approved withdrawals stay in the
verified-cash controls. Customer and mission funds remain separate.

No aggregate earnings or customer totals are inferred from a truncated page. The
workbench shows up to 200 recent records and labels total records as records, not
verified customers. Broken bindings return an explicit review state, not an
invented zero-success conversion.

## Owner operating sequence

1. Sign in to the private mission dashboard → **Customers & work**.
2. Review the two service scopes; preview owned, non-sensitive input if desired.
   Choose a proposed price based on actual scope/capacity. Prepare—not publish—a
   listing pack. Verify an authentic account before any manual publication.
3. When a real request exists, record its source and permissions. Prepare one
   response, inspect it, and manually reply in the permitted original channel.
   No acquired customer is claimed until real demand actually arrives.
4. Agree the displayed exact scope with the real buyer. Establish lawful account,
   contract and receiver verification through the appropriate existing connector.
   That integration is currently disabled without approved real verifiers.
5. Bind the actual authorized work ID. Produce the deliverable from authorized
   input, review it, and approve its exact hash. Manually use the existing connector
   workflow; this module neither submits work externally nor reports human hours.
6. Complete provider confirmation and independent USD settlement through that
   connector. Inspect the attributed receipt and the separate verified-cash wallet.
   Never use an uploaded screenshot, CSV, checkbox or sample receipt as payment.

API: owner-authenticated `/api/customer-work`; GET overview or `/ID`; POST
`listing`, `preview`, `record`, `response`, `stop`, `bind`, `produce`, `approve`.
Mutation uses existing bearer/CSRF rules. No public intake, send, publish, signup,
scrape, proof-import, credit, withdrawal or arbitrary execution endpoint exists.

- Explicit owner approval before publication/contact/contracts or money actions.

The owner has no approved publishing property and no receiving provider. Neither
was invented or configured. No real customer, listing publication, paid order,
external delivery, earnings, spending, withdrawal or deployment is claimed.
